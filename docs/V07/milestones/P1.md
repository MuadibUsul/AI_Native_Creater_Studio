## 目标

P2 要让 DSH Fork 驱动 Agent 轮次，在那之前先在 ANCS 侧把三样东西准备好：

- 一个可切换、可回退的运行时入口；
- 一份 DSH 侧照着实现的工具桥契约；
- 一份鉴权方案。

同时修好基线里的测试隔离问题，让 legacy 与 DSH 的对照能建立在一次干净的全量运行上。

**本阶段不改变任何用户可见行为**：legacy 仍是缺省也是唯一可用的运行时。所以界面与浏览器验收"不适用"。

**`video-tool.v1` 契约包含：**
- 由 ANCS 工具描述派生的桥上描述：只有 READ 工具可并行；看画面的工具截止时间更长。

**桥鉴权设计包含：**
- 一轮一令牌，专用密钥 `ANCS_AGENT_BRIDGE_KEY`，不与任何现有密钥共用。
- 每次调用的 8 步校验：信封 → 验签 → 范围 → 轮次仍在进行 → 权限 → 工具 → 幂等 → 与 legacy 相同的门禁与执行。
- 出网限制、审计字段，以及 14 条 P2 必须通过的测试（B01–B14）。

## 测试隔离：调查结果（更正 P0 的判断）

**P0 的判断错了。** P0 审计把 `render-execution.integration.test.ts` 的 2 项失败归因于"并行时等锁"。但集成项目配置了 `fileParallelism: false`，测试文件逐个运行，不存在并行文件之间的锁竞争。

**找到并修好的根因：测试认领到别的测试留下的任务。**

- P1 第一次全量运行时，`footage-description-cap.integration.test.ts` 4 项全部失败，报"认领不到任务"。这个文件在 P0 时通过。
- 按全量运行的记录，在它之前跑的是 `voice-clone.integration.test.ts`。依次单独运行之后确认：
  - voice-clone 上传素材后，会在队列里留下 2 个 `MEDIA_PROBE` 任务，这对上传来说是正常的；
  - `claimJob` 不分工作区，按先后认领同类任务。footage-description-cap 于是认领并执行了 voice-clone 留下的探测任务，而不是自己的；
  - 它自己的画面理解任务因此根本没有建出来，下一次认领拿到空值。
- 把这两个文件依次运行，可以稳定复现 4/4 失败；先把残留任务消耗掉再跑，4/4 通过。
- 测试文件的运行顺序每次可能不同，所以这类失败时有时无。

**修复**（`4289dc7`）：
- `claimJob` 增加可选的 `workspaceId`，只认领该工作区的任务。Worker 不传这个参数，生产行为不变。
- footage-description-cap 改为只认领自己工作区的任务。在 15 个调用 `claimJob` 的测试文件里，只有它"只清理自己的数据，却全局认领"；其余 14 个在每个测试前删除全部工作区，残留任务也一并被清掉。
- 新增 jobs 集成测试：按工作区认领时，忽略别的工作区更早的任务；不传工作区时照旧认领。
- 在同样的复现条件下（队列里有 2 个残留探测任务），修复后 4/4 通过，残留任务原样保留、没有被动过。

**`render-execution` 的那次钩子超时没有再出现。** 记录如下：
- 单独运行：2/2；
- 28 个 worker 集成文件一起运行：108/108，期间没有任何语句等锁超过 3 秒；
- P1 第一次全量运行：通过，测试库也没有记录到超过 2 秒的语句。

那次失败的原因仍未确定，先保留为"观察项"。没有为它调大超时，也没有改那 68 个"删除全部工作区"的测试文件，两者都只会掩盖问题。

**修复后的全量集成确认运行：进行中**（结果出来后补在这里）。
