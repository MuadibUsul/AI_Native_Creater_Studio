# 上传视频太慢：定位与提速（2026-10-30）

所有者反馈："upload video is so slow"。本记录写清慢在哪里、改了什么、实测前后对比，以及代码之外需要所有者决定的事。

## 结论

用户感受到的"上传慢"大部分不是传字节，而是**传完之后素材迟迟不能用**：

1. **探测**（素材变成"就绪"之前必须完成）里有一步用 `ffprobe -show_frames` 读前 120 秒的帧时间戳。它会单线程解码每一帧：30 秒 4K HEVC（手机常见格式）要 **69 秒**，比完整解码整段文件（19 秒，多线程）还慢。契约字段本来就叫 `sampledPacketCount`，读包时间戳不需要解码，结果相同，只要 **0.1 秒**。
2. 探测里每个子进程固定 5 分钟超时，超时就判整段素材失败。共享 VPS 上一段 10 分钟的 4K HEVC 完整解码会超过 5 分钟，**素材永远不可用**（看起来就是"一直在处理"然后失败）。
3. **镜头索引**把全分辨率原片解码三遍（缩略图、镜头边界、黑场各一遍）：30 秒 4K HEVC 要 76 秒。Worker 默认只有 1 个任务槽，索引期间后面的任务（包括 AI 对话轮次）都在排队。
4. 传字节本身：本机不限速时 183 MB 用 5.8 秒（31 MB/s），服务端不是瓶颈；模拟线路下能用到链路带宽的 82%–92%。剩下的两个风险：
   - 共看片室里一次选多个文件时，所有文件**同时**上传，平分同一条上行带宽，全部要到最后才一起可用，服务端还要同时缓冲多路分片（生产 API 容器内存上限 640m）。
   - 确认上传时服务端要合并分片再把整文件读一遍算 SHA-256；Web 的 `/api/v1` 转发默认 **30 秒**不响应就断开（浏览器收到 500）。几 GB 的素材在共享 VPS 上会超过 30 秒，服务端其实完成了，界面却显示"上传失败"。

## 改动（按层）

| 层 | 改动 |
|---|---|
| contracts | `ObjectStorageAdapter.composeObjects` 返回 `ComposedObject { checksumSha256 }`：复制途中读过全部字节的实现带回整文件 SHA-256，在存储内部拷贝的实现返回 null |
| providers | 本地存储合并分片时同时算 SHA-256（一条 pipeline 写到底：写盘出错与清理照旧，顺带去掉每个分片累加流监听器的 MaxListeners 警告）；S3 驱动返回 null，调用方照旧另算 |
| domain | `confirmUpload` 优先用合并时算出的校验和，省去再读一遍整文件；没有时与原来一样调用 `computeObjectSha256` |
| worker | 探测：`-show_frames`（解码）改为 `-show_packets`（不解码），容器标记丢弃的包（flags 含 D）不计；完整解码检查的时限 = 基础时限 + 素材时长 × 2。索引：缩略图、镜头边界、黑场合成一次 ffmpeg（一次解码 `split=3`），三路输出与分开跑逐字节相同 |
| API / SDK | 不适用（接口与行为不变） |
| web | `next.config.mjs` 的 `experimental.proxyTimeout` 放宽到 10 分钟；共看片室多个文件排队一次传一个（每个文件 6 片并行，SDK 上限），排在后面的显示"排队等待上传 / Waiting to upload"（中英） |
| tests | 本地存储：合并返回的校验和与整文件一致、24 个分片不再出 MaxListeners 警告、缺分片时失败且不留半成品；探测：编辑列表裁掉的包不计入、解码时限随时长增长；索引：一次解码仍得到全部缩略图和片尾的切点与黑场 |

不改变的：探测仍然完整解码整段文件（保证"可解码"这一能力判断不变）；索引结果的格式与处理器版本不变（已有索引不会被判过期）；没有改 Provider 业务逻辑。

## 实测

环境：本容器 4 核、16 GB；真实 API（Fastify）+ 本地存储 + PostgreSQL 16 + 真实 FFmpeg 6.1 Worker；脚本是一次性的（`scripts/.tmp-upload-bench.mjs`，不入库）。

### 一段 30 秒 4K HEVC 10-bit（152 MB，手机常见格式）

| 阶段 | 之前 | 之后 |
|---|---:|---:|
| 传完到**素材可用**（探测完成） | 88.9 秒 | **17.7 秒** |
| 探测任务 | 88.8 秒 | 17.2 秒 |
| 预览代理 | 26.4 秒 | 24.8 秒（未改） |
| 镜头索引 | 80.3 秒 | 42.7 秒 |
| 传完到全部处理完（代理 + 索引） | 196.2 秒 | **85.3 秒** |

分项（同一文件单独计时）：帧时间戳 68.7 秒 → 包时间戳 0.11 秒；索引三遍 76.4 秒 → 一遍 42.4 秒。

### 一段 60 秒 1080p H.264（183 MB，24 Mbps）

帧时间戳 8.8 秒 → 包时间戳 0.13 秒；采样结果（1800 个、间隔 512）完全相同。

### 确认上传（1.1 GB，经 Next 转发）

确认耗时 7.3 秒 → 4.7 秒。本机页缓存能装下整个文件，第二遍读取几乎免费；生产机可用内存约 1.7 GiB、读盘更慢，省下的那一遍整文件读取占比更大。

### 模拟线路（往返 250 ms、上行 40 Mbps，183 MB）

| 每个文件同时传的分片 | 用时 | 占链路带宽 |
|---:|---:|---:|
| 3（原来） | 44.7 秒 | 82% |
| 4 | 42.0 秒 | 87% |
| 6（现在） | 39.7 秒 | 92% |

另：往返 180 ms、上行 20 Mbps 时 3 片为 92%；本机不限速时经 Next 转发与直连 API 无差别（5.3–5.8 秒）。

### 真实浏览器

`scripts/.tmp-upload-queue-browser.mjs`（一次性）：真实 Chromium + 生产构建的 Web（`next start`）+ 真实 API/Worker；用 DevTools 把上行限到 2 MB/s，一次选 3 段素材。

- 中文、英文各一遍：第一段显示"上传 x%"时，另两段显示"排队等待上传 / Waiting to upload"；
- 第二、三段的上传意图分别在前一段确认后 86–100 ms 才创建（确实一次一个）；
- 三段全部就绪，无页面错误。

截图：`docs/verification/artifacts/upload-speed/01-queue-zh.png`、`01-queue-en.png`（排队中）、`02-ready-zh.png`、`02-ready-en.png`（前两段已就绪、第三段处理中）。

## 需要所有者决定或执行的（代码之外）

1. **部署新版本**：按上次的流程重新构建 runtime / worker 镜像并更新 darely.xyz，改动才会在线上生效。
2. **离用户远的上行线路**：传字节的速度最终受用户到服务器那条线路限制（darely.xyz 在海外 VPS，从国内上传常见往返 150–250 ms 且丢包）。代码里已有 S3 兼容驱动（`ANCS_STORAGE_DRIVER=s3`，R2 / OSS 等），浏览器用预签名地址直传到离用户近的对象存储，字节不再经过 VPS。这涉及存储费用与区域选择，需要所有者决定。
3. **Worker 任务槽**：生产是 1 个槽，素材处理期间 AI 对话轮次会排队。内存允许时可把 `ANCS_WORKER_SLOTS` 调到 2（Worker 容器上限 1280m，需先观察内存）。

## 发现但未改（单列，待决定）

- 恶意内容启发式扫描对**每个分片**都检查"MZ 文件头"。视频中间的某个分片恰好以 `4D 5A` 两个字节开头时（概率约 1/65536 每片，2 GB 文件约 0.4%），上传会被误判拒绝。建议只对第一个分片做文件头检查；涉及安全扫描逻辑，本次没有改。
- 完整解码检查仍在"素材可用"之前（4K HEVC 约每 30 秒素材 19 秒）。若改为与预览代理（本来就完整解码一遍）合并，素材可在几秒内可用，但"可解码"的判断会推迟到代理完成，属于行为变化，需另行决定。
