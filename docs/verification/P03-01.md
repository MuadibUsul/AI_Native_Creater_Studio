     - **Outbox 派发**：`runJobDispatch`（消费未发布 `job.queued` → 队列适配器投递 **仅任务 ID + 路由** → 标记 published；**队列不可用时不标记**——投递中断重跑即恢复）；`runMaintenanceTick`（租约回收 + 派发，可重入）。

- **验收条款对照**：
  1. **"事务提交后投递中断可恢复，不丢任务"** → 通过（直接证据）：创建任务与 `job.queued` 事件**同事务**；模拟投递中断（队列适配器抛错）→ `report.failed=1`、事件**保持未发布**、`enqueuedAt` 为空；重跑派发 → 投递成功（任务未丢）。此外租约回收路径也让"已认领但 Worker 崩溃"的任务回到 QUEUED 并可再次派发。
  2. **"任务依赖"** → 通过：依赖未满足时 WAITING_DEPENDENCY（**不产生派发事件**）；依赖成功后同事务升级 QUEUED 并派发；依赖失败 → 依赖方 FAILED_FINAL（`DEPENDENCY_FAILED` 含阻塞依赖与状态）——无永久等待。
  3. **"状态机"** → 通过：9 状态机 + 非法迁移 409；`PROVIDER_QUEUED` 租约到期 → `needs_reconciliation` + `SUBMISSION_UNKNOWN`（不自动重复付费，§5.6）。
  4. **"BullMQ 调度"** → **部分为契约级验证（诚实记录）**：适配器已实现（只投递任务 ID + 路由、任务 ID 幂等、fail-closed），用注入式工厂做契约级测试；**真实 Redis 端到端未执行**（CI 未加 redis service，本地未启 Redis）——已在剩余风险与交接中登记为 P03-02 义务（该任务的验收本就覆盖"各关键点杀 Worker 后可继续"，届时一并加 redis service）。
  5. **REQ-70-02（不阻塞 UI）** → 通过：任务 API 返回 202 语义的 job 资源 + `job.*` 事件经 P02-06 的 SSE 推送（事件产生方已从"预留位"变为真实产生）。
- **本次修复的工程问题（诚实记录）**：
  1. **R1/R6 依赖方向**：API 的集成测试最初 `import '@ancs/worker'`（apps↔apps，违反 R1 且模块不可解析）——把执行器闭环测试移到 `apps/worker` 自己的集成测试（vitest integration include 扩展 `apps/worker/src/**`）。
  2. **at-least-once 的现实**：重试任务会让"旧的未发布 `job.queued` 事件 + 新事件"都参与派发 → 同一任务可能被投递两次；这是 Outbox 的**至少一次**语义，正确性由认领的 CAS（SKIP LOCKED + 状态条件）保证（测试断言"重复消息不产生第二个执行者"）。
  3. **secrets:check 误报**：测试中的 `secretInput` 字段名触发凭据启发式——改为 `markerInput` 并加说明注释（不豁免、不隐藏）。
  4. **未知任务类型**：执行器拒绝静默结束——未知类型直接 FAILED_FINAL 并在错误中给出已注册类型清单。
