  4. **编辑处理器扩展**（`domain/src/edits.ts`）：
     - **富补丁**：每个内容事件的 `patch` 记录受影响 Scene 的**前后内容快照**（narration/visualIntent/type/duration/组件/绑定/transition/locked/status），作为补偿与重放的唯一事实来源；
     - **restore_scene**（按 revision 重放）：单遍扫描内容类事件（insert/duplicate=基线，update/split 尾部/restore 递增）在目标 revision 截获；越界/当前 revision → 409；锁定场景拒绝；恢复产生新 revision（内容与锁状态一并回到目标）；
     - **restore_project_version**（整项目）：从不可变快照重建场景集（移除快照外、按序 upsert 快照内、重建缺失场景**复用原 id**），新 revision、**强制产生 RESTORE 快照**；
     - **同请求同 Scene 多操作**：预期 revision 在该 Scene 首次触达时校验一次，后续操作顺序应用（条件更新以"事务内读取的原始 revision"为依据，修复多操作 revision 漂移）；
     - **补偿链路**：`compensation {kind, originalEventId, originalAction, originalOperation, intentText}` → 事件 action 加 `UNDO_`/`REDO_` 前缀、`compensatesEventId` 指向、patch 记录 `originalAction/originalOperation`；
     - **结构操作**集合扩至 restore_scene / restore_project_version（`baseProjectRevision` 精确匹配）；
     - **自动快照**：AI 重编导**前**（pre-apply 行状态 + 事件前水位线，reason AI_REDIRECT）、RESTORE 后、每 N 事件（默认 50，`autoSnapshotEveryEvents` 可配，按 seq 水位线计数）——全部与状态/事件/Outbox 同事务。
  5. **Undo/Redo 服务**（`domain/src/undo-redo.ts`）：以补偿事件实现（历史只增不改）。生效分析：事件被"最近的 UNDO_ 引用"则失效、被"指向该 UNDO_ 的 REDO_ 引用"则重新生效；撤销目标 = 最新仍生效的非补偿事件；逆操作按事件 patch 构建（insert/duplicate→delete、delete→insert 复用原 id、split→删尾+源写回、reorder、update/lock/project、RESTORE_PROJECT_VERSION→恢复 beforeVersionId）；**Redo = 最近一次撤销所记录的原始操作（LIFO）**，新的普通编辑使 `undo.seq < 最新普通事件 seq` 从而**结束重做分支**（§4.8）；锁定场景自动插入显式解锁。
  6. **API**（`apps/api/src/routes/projects.ts`）：`POST/GET /projects/:id/versions`、`GET /projects/:id/versions/:versionId`、`POST /projects/:id/undo`、`POST /projects/:id/redo`（沿用"先定位 workspace → 统一授权入口"模式；写操作需 `project:write`）；SDK 新增 `projects.versions.{create,list,get}`、`projects.undo/redo`。

  1. **"恢复产生新 revision"** → 通过：`restore_project_version` / `restore_scene` / 每次 Undo/Redo 均使项目 revision +1、被改场景 revision 递增（测试断言 a 的 revision 1→2→3 恢复 3、restore 后 4）；恢复本身也作为事件落库。
  2. **"旧版本和账本不被改写"** → 通过（双层断言）：旧版本详情（含快照本体 JSON）在编辑与恢复前后**逐字节相同**；恢复后事件总数 = 原事件数 + 新增（编辑 3 + 恢复 1），且**前缀事件逐字段等于**恢复前快照（无 UPDATE、无删除；`edit_events` 仅追加）。
  3. **AC-19（Restore 历史版本 → 新 revision，历史费用不变）** → "新 revision + 历史不改写" 已在本任务验证；**"历史费用不变"维度在 P03-05 成本账本落地后才可实测**（当前无成本数据），结构上由"恢复只追加事件/版本、从不改写既有行"保证。已记入剩余风险。
  4. **自动快照时机（REQ-23-03）** → AI 重编导前（AI_REDIRECT，快照内容为 pre-apply 旧状态且可直接恢复）、手动 Save、每 N 事件（seq 水位线）已实现并有测试；FINAL_RENDER / PUBLISH 两个时机随 P07-05/P12 的真实渲染与发布任务接入（接口已就绪）。

- **本次修复的工程问题（诚实记录）**：
  1. **循环外键导致的行类型坍缩**：`projects.current_version_id → project_versions.id` 与 `project_versions.project_id → projects.id` 使两张表的 `$inferSelect` 互相引用、TS 退化为索引签名（TS4111 满屏）——移除 projects 侧 FK（版本行的级联删除由 project_versions 一侧负责），迁移 0008 记录。
  2. **重放的场景关联**：`insert_scene` 事件的 patch 不含 sceneId（只有 afterSceneId/sceneDraft），重放最初以 patch.sceneId 关联导致基线丢失（restore 回到错误的 revision）——改为以**事件的 sceneId 列**为准，并在 DB 查询中带出该列。
  3. **同请求多操作的条件更新缺陷**：脏场景的最终条件更新原以 `revision-1` 为条件，同一 Scene 两次操作后失配（伪造的并发冲突）——改为以事务内读取的**原始 revision** 为条件（行锁下必中，作为最终防线）。
  4. **AI 发起人不可入 createdBy**：`project_versions.created_by` 外键指向 `user`，AI/SYSTEM 触发时写 actorId 会违反外键——AI 快照的 createdBy 记 null，发起链路经 EditEvent.actorId 追溯（测试断言）。
  5. **撤销删除的身份稳定**：最初补齐方案会因 Scene id 变化使"撤销→重做"链中断（404）——引入补偿专用 `restoreSceneId`/`restoreTailSceneId` 复用原 id，保证历史事件与引用（资产绑定等，P02-04 起）持续有效。
