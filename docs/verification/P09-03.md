- **验收条款对照**：
  1. **"支付成功事件只能入账一次"** → 三重保证并逐项断言：事件闸门（同 providerEventId → DUPLICATE、余额不变）+
     账本部分唯一索引（每 billing_event 至多一条入账；重复退款至多一条 refund_of）+ 集成测试直接断言"重放后余额不变"。
  2. **"网页跳转不能作为入账依据"** → 结账（`startCreditCheckout`）只生成渠道 URL；集成断言"购买后余额为 0"；
     Web 购买只展示链接、不自动跳转且明示"网页返回不代表入账——入账以渠道事件为准"；入账唯一入口 =
     `/webhooks/payments` 验签事件（P09-02 已断言结账后状态 NONE）。
  3. **"充值、赠送、扣减、退款、账单展示及对账"** → 充值（事件入账）/赠送（管理端）/扣减（既有生成链路消耗，
     P03-05）/退款（扣回，幂等）/账单（语句 API + Web 页）/对账（事件↔账本 API + 按钮）逐项交付并有测试。
- **本次修复/发现的工程问题（诚实记录）**：
  1. **退款条目类型的口径修正（重要）**：首版把"退款"写成 `REFUND` 条目类型——与本仓库既有账本契约冲突：
     `amount` 恒非负、**符号由 entryType 决定**，且 `CREDIT/REFUND 为 +`（REFUND 语义 = "把已扣额度退回给用户"）。
     "购买退款"方向相反（钱退回渠道 → Credits **扣回**，负向），全表唯一负向类型是 `DEBIT`——修正为
     `DEBIT + reference_type='refund_of'`（与使用扣减以 referenceType 区分；集成测试暴露该错误后修正）。
  2. **vitest alias 缺项**：`@ancs/providers-mock-payments` 未在 `workspaceAliases` 中——测试运行时解析到**陈旧 dist**，
     掩盖了源码变更（结账 URL 仍为旧语义）。补齐 alias 后暴露并修复 mock 的 createCheckout 签名（契约已支持
     `packCode`/`planKey:null`，实现未跟进）。
  3. **管理端路由的显式校验**：grant/refund 采用非类型化路由 + 手动 zod（与 P08-02 admin 面一致），
     校验失败返回 400/422 明确 envelope，不静默。
