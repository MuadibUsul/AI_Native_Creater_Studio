- **验收条款对照**：
  1. **"重复确认幂等"** → 通过：二次确认返回一致结果、版本数不变、Intent 只完成一次（服务层断言）；HTTP 层经 SDK 复确认同样成立。
  2. **"伪造 MIME 不可 Ready"** → 通过：声明 `image/png` 上传文本内容 → **415 UNSUPPORTED_MEDIA_TYPE**（details 含 declared/sniffed），版本与资产置 FAILED、**对象被删除**、再次确认仍 409（不会因重试变 Ready）。判定基于真实魔术字节（有签名类型必须命中兼容签名）。
  3. **"越权对象不可 Ready"** → 通过：跨 workspace 的 confirm/get/download-url/list 全 404（抗枚举）；上传端点不接受任何客户端可控键参数（额外 `key=` 被忽略，文件只落在 token 的键）；上传 token 用于下载端点 → 403；篡改签名/过期 → 403；VIEWER 成员可读不可写（403 含 requiredCapability=asset:manage）。
  4. **"不完整上传不可 Ready"** → 通过：对象缺失 → 409 OBJECT_MISSING；实际大小 < 声明 → 409 SIZE_MISMATCH（保持 PENDING_UPLOAD 可重试，补传完整后确认成功）。
  5. **校验和** → 通过：服务端流式计算 SHA-256；与客户端（意图或确认阶段）声明不符 → 409 CHECKSUM_MISMATCH + FAILED + 清理对象；一致时记录于版本行（含探测出的图片尺寸）。
  6. **去重（§26.3）** → 通过：意图阶段（客户端预计算 checksum 命中 → 不创建对象直接绑定既有资产）；确认阶段（未预声明 checksum 的重复内容 → 复用既有对象、删除冗余、记录 dedupeOf）。
  7. **Signed URL scope（§51）** → 通过：单元层（签名/用途/TTL/路径穿越）+ HTTP 层（篡改 403、用途不符 403、过期 403、键不可控）双重证据。
  8. **Provider credential isolation（§51）** → 通过：所有资产响应与错误信封不含签名材料/`http://`；下载 URL 只出现在专门端点；SDK 客户端对象不含任何存储配置。
- **本次修复的工程问题（诚实记录）**：
  1. **R3 依赖约束**：domain 不得依赖 providers/*（含 devDeps）——服务层集成测试放在 `apps/api`（允许依赖 providers），domain 只保留接口依赖。
  2. **本地端点前缀**：存储路由最初写全路径导致 `/api/v1/api/v1/...` 404——改为在 API_PREFIX 注册块内使用相对路径（`/storage/upload`）。
  3. **错误信封**：存储端点初版直接返回裸 error 对象——改为统一信封（`errorEnvelope()`），与全局错误处理一致。
  4. **可空校验和**：资产版本契约初版强制 64 位十六进制校验和，导致 UPLOADING/FAILED 版本无法序列化——改为可空（READY 必有）。
  5. **伪造 MIME 判定漏洞**：初版 `mimeMatches` 对"无签名内容"一律放行（文本冒充 PNG 会通过）——改为**有签名声明类型必须命中兼容签名**，并补单元测试锁定。
  6. **上传 URL 端口**：适配器 publicBaseUrl 需在测试 listen 后回填（本地驱动 URL 由服务端生成）。
  7. **场景草稿保真**：`sceneDraft` 增补 `assetBindings`，避免"撤销删除 Scene"丢失绑定。
