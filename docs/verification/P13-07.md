## 实现摘要

1. **公共契约**：新增 `CMS_WRITEBACK` Job、目标/尝试状态、固定事件 `creator_video.render.ready_for_review`、回调 DTO、签名头常量及 `CmsWritebackSender` I/O seam。事件明确表示“已就绪，等待人工审批”，不表示已发布。
2. **迁移 0046**：新增 `cms_writeback_targets` 与 append-only `cms_writeback_attempts`。目标按 workspace 唯一；Secret 仅保存 AES-256-GCM 密文封套、掩码和 key version；尝试按 `(delivery_id, attempt_number)`、`(job_id, job_attempt)` 唯一，并用首尝试部分唯一索引保证同一目标和 Render 仅形成一次逻辑 delivery。
3. **配置与调度**：目标支持 URL、Secret、启停的部分更新，首次必须同时给 URL 和 Secret。URL 复用 `assertSafeUrl` 并额外拒绝 credentials/fragment。Render 在 QA→READY 的同一事务内，为 CMS 来源与 ACTIVE 目标创建稳定 payload、首个 attempt、SYSTEM Job 与 `job.queued` Outbox；无 CMS 来源、无目标或已禁用时正常 READY 且不建 Job。
4. **发送与恢复**：Worker 使用最新目标 URL 和 Secret，按 `timestamp.rawBody` 生成 HMAC-SHA256；10 秒超时、16 KiB 响应上限、响应头白名单、3xx 不跟随。2xx 成功；408/425/429/5xx 与网络错误最多自动发送四次；其余 4xx、SSRF、目标禁用和签名配置错误最终失败。失败只更新 attempt/Job，Render 保持 READY。
5. **幂等语义**：首次生成的 `deliveryId`、`occurredAt`、规范化正文和正文 SHA-256 在自动重试、崩溃恢复和人工重发中保持不变；每次发送重新生成 timestamp/signature。Worker 在“已发送但未完成记录”后恢复时将旧 PENDING 标为 UNKNOWN，并创建新 attempt。
6. **真实 HTTP Sender**：只用 Node HTTP/HTTPS；DNS 全量解析后，任一地址为回环、私网、链路本地、CGNAT、组播或保留地址即拒绝；连接固定到已验证 IP，同时保留 Host 与 HTTPS SNI，防止 DNS rebinding。
7. **API/SDK**：交付目标 GET/PUT、attempt 列表、delivery 人工重发四个 REST API，以及 SDK 的 `getWritebackTarget`、`upsertWritebackTarget`、`listWritebackAttempts`、`retryWriteback`。所有查询带 workspace scope；读取需 `workspace:read`，配置/重发需 `workspace:update`；跨租户统一 404。
8. **UI**：不适用。P13-07 的交付面为 CMS 机器接口和 SDK。

## Mock / 真实边界

- Domain/Worker 集成使用 `ScriptedSender` 注入 2xx、429、5xx、3xx 和崩溃时点，用于确定性验证状态机、幂等、重试、截断和恢复；它不冒充第三方 CMS 实测。
- 真实网络实现 `createHttpCmsWritebackSender` 已在 Worker 默认装配，DNS 固定连接与 SSRF 规则由单元/安全路径验证。本任务不依赖任何第三方 CMS 凭据，未向外部 CMS 发请求。
- 外部 CMS 的必要幂等约束：以 `deliveryId` 至多应用一次；网络结果 UNKNOWN 时，ANCS 会用同一 `deliveryId` 再发。
